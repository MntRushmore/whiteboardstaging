# Model bench: cheap and fast models for the three model jobs

Run 2026-09-27. Generated by `npm run eval:models` (`src/__eval__/models/**`); every response is cached under `src/__eval__/.cache/models/`, so a rerun is free and reproduces these numbers. Prices and capabilities from the OpenRouter catalog fetched 2026-09-27.

**Spend:** $0.7668 in 714 OpenRouter calls in total (cap $4.50 of the $5.00 approved; $0.0000 of it in the run that wrote this file). Cost per call is OpenRouter's own `usage.cost`.

**Do not use**
- `openai/gpt-5.4-nano` for repair. It fixed 0 of the 18 real misreads (it hands back Mathpix's read) and broke 3/20 correct ones (`u = 3` → `v = 3`, `|x - 1|` → `|x - 11|`, `a + b + c` → `0 + b + c`), which is worse than no repair. On the text jobs it is fine (24/25 setups, 23/25 answers) and the cheapest.
- `google/gemini-3.5-flash-lite` on the solve route. 12/25 replies had no valid JSON line because the LaTeX was unquoted (`"latex": u = x`), and a JSON Lines route cannot turn on JSON mode.
- `qwen/qwen3.8-flash` anywhere. It ignores `reasoning: low/minimal`, spends 270–930 reasoning tokens, has a p50 of 5–19 s, and ran out of tokens on 4/25 solves and 3/44 repairs (empty replies).
- `anthropic/claude-haiku-4.5` for the text jobs. It is accurate on setups (25/25) but has a p50 of 4.9–7.0 s with low reasoning, and the highest cost per call on job 1 (second-highest on job 2).

**How to run repair, if it ships.** Do not run it on every line. The scoreboard's misread rate is 3.3%, so any break rate above about 2.5% undoes the gain, and 0 breaks in 20 controls only bounds the break rate below about 15% (rule of three). Collect more controls before trusting it on every line. Until then, run it only on a signal: the engine cannot read the line or finds it inconsistent with the line above; a symbol that is odd in context (`\theta`, `\Delta`, a digit used as a base like `6^{x}`, `0 =` where letters were used above); or a letter the lines above never use. Mathpix's own confidence is no trigger: `a = 2` read as `0=2` came back at 0.99. At $0.35 per 1000 calls the cost does not matter. The latency does: it is a second round trip after Mathpix (about 0.9 s).

**The word-problem job is saturated.** Every model got 24 or 25 of 25. The only misses were one garbled line and setups the engine cannot solve (below). This bench cannot separate the top models here, so latency and cost decide.

**Product findings (no product code was changed)**
1. **The step guard rejects every `+ C`.** It treats `C` as a symbol from nowhere (`unknown-symbol`), so no antiderivative from any model is ever drawn. That covers 7 of the 25 fallback problems. With `C` in scope, the top models' usable rate goes from 52–60% to 80–84% (the "usable if + C were allowed" column).
2. **The guard drops other right answers too:**
   - `= \boxed{1}`: the box is only unwrapped when it wraps the whole step.
   - `\boxed{e}`: a bare constant.
   - any step containing `\frac{d}{dx}` (L'Hôpital, for example), which it reads as a new symbol `d`.
   - `u = x, \quad dv = e^{x} dx`: the `v` of `dv`.
   - `\binom{10}{3} = 120`.
   - interval notation.
3. **The solve prompt never states the board's answer conventions.** It should say: several answers as a list `x = 2, \ x = 3`; no `\text{or}` or `\text{for}`; no interval notation; one relation per step. Between 4% and 29% of each model's solutions had a step with words, and most models answered inequalities in interval notation. A few lines in `SOLVE_SYSTEM_PROMPT` would fix this.
4. **`chatJson` parses with plain `JSON.parse`.** It is the parser behind the vision fallback in `/api/live/recognize`. Even in JSON mode, 5 of 225 word-problem replies wrote `\frac` or `\times` with a single backslash, and `JSON.parse` silently turns those into a form feed or a tab. The bench parses with `repairJsonEscapes`, the repair the JSON Lines path already uses; `chatJson` should use it too. Separately, DeepSeek sometimes writes its reasoning into the content despite JSON mode (3/44 repair replies were not JSON).
5. **The engine cannot solve a non-linear system by substitution.** `l = w + 3` with `l \cdot w = 40` fails in `solveFromLines`. Three models set wp-05 up this way (a correct setup) and scored nothing for it.

## How each job is run

| job | items | prompt | output | settings |
| --- | --- | --- | --- | --- |
| 1. word problems | 25 school word problems with known answers | bench prompt `WORD_SETUP_SYSTEM_PROMPT` (wordProblems.ts): set up, never calculate | JSON `{unknown, lines[]}`; the lines go through `localSolve` (the board's local Solve) and the engine's answer is compared numerically | reasoning low, max 1500 tokens, JSON mode, timeout 60 s |
| 2. solve fallback | 25 problems `localSolve` returns `source: null` for | the product's `buildSolveMessages` (prompts/solve.ts), unchanged | JSON Lines parsed by the route's `jsonlToEvents` + `SolveStepSchema` (8-step cap, last step boxed), then every step through `createSolveStepGuard` + `engineParsesStep` | reasoning low, max 1500 tokens (as /api/live/solve), timeout 60 s |
| 3. misread repair | 18 real Mathpix misreads + 6 synthetic + 20 correct reads (controls) | bench prompt `REPAIR_SYSTEM_PROMPT` (misreads.ts): image of the ink + Mathpix's LaTeX + the lines above | JSON `{latex, changed}`, judged by the handwriting scoreboard's `judgeRead` against what was written | reasoning minimal (Anthropic: none), max 800 tokens, JSON mode, timeout 45 s; PNG 2871–14376 bytes |

Every call: temperature 0 where the model takes it (GPT-5.4 and Sonnet 5 do not; their default is used), `provider.sort: latency` as the Live routes stream with, at most 4 in flight. Latency is wall clock per call, non-streaming (the board writes a model's steps only when the stream ends, so the whole reply is what the student waits for). Every model was piloted on the first 5 items of each job before the rest ran.

## 3. Misread repair (vision)

**fixed** = a misread (real or synthetic) comes back as what was written (exact or the same maths). **broke** = a CORRECT read (control) comes back as something else (a failed call or an unreadable reply keeps Mathpix's read, so it is a failure, not a break). The synthetic misreads turned out to be guessable from the LaTeX alone (every model fixed all six, including one that fixed no real misread), so **fixed (real only)** is the column that measures reading the image. **net / 1000 lines** = real misreads fixed minus correct reads broken if the repair ran on every line, at the scoreboard's misread rate (3.3% of lines): the cost of a false correction is paid on the ~97% of lines Mathpix already reads right.

## Caveats

- **Small samples.** 25 / 25 / 44 items per job, one run at temperature 0: one item is 4–5 percentage points. Differences of one or two items are noise; read the tables as tiers, not a leaderboard.
- **Latency** is one machine, one afternoon, through OpenRouter's latency-sorted routing; p95 over ≤ 25 calls is close to the maximum. Cached reruns report the first run's timings.
- **Prompts.** Job 2 uses the product's solve prompt verbatim; jobs 1 and 3 use bench prompts written for this test (a better prompt could move every model). The repair prompt names the classes of confusion Mathpix makes (look-alike letters and digits, case, bars, lost limits), which are also the classes in the test set; the synthetic items only partly offset that.
- **Answers are judged numerically** (`answers.ts` over the scoreboard's oracle). An answer in a form the oracle cannot read — a tuple the parser does not know, degrees for a radian question — counts as wrong.
- **Handwriting is the tutor's own hand** (the handwriting scoreboard's ink), not a student's; images are rendered from the strokes at up to 2× the page scale.
