# Safari / iPadOS (WebKit) — QA and fixes (2026-10-03)

Branch `fix/webkit-ipad` (from `release/ink-and-board` at `b37d640`). Scope: what breaks or feels
wrong in Safari's engine, above all on an iPad with an Apple Pencil, which is where most paying
students write. Every earlier pass ran in Chromium only (`QA-2026-10-02-feel.md`,
`QA-2026-10-02-reliability.md`). Sync/backups/image upload/the balance hook (`fix/sync-followups`)
and sign-up, the login layout, bug-report data, the recognize route schema and the full E2E
(`fix/release-polish`) are other lanes: what turned up there is listed at the end, not changed.

## Method

- `next dev --webpack -p 3002` against the shared local Supabase (user `qa-webkit@example.com`), real
  OpenRouter / Mathpix calls (a handful of lines and one Ask request, no loops); a production build
  (`next build` + `next start -p 3002`) for the final smoke and the bundle numbers.
- Playwright 1.63 **WebKit 26.6** (the macOS port of Safari's engine), headless, with the `iPad Pro 11`
  and `iPad (gen 7)` descriptors upright and sideways, `iPhone 14` upright and sideways (`isMobile`,
  `hasTouch`), and a 1440x900 desktop window. A real iPad's Safari asks for the desktop site and sends a
  **Mac user agent**, not the descriptors' `iPad; CPU OS 12_2` one; the runs that matter were repeated
  with an iPadOS desktop UA, because tldraw branches on it (below).
- How input was driven, and how that differs from the Chromium scripts (`feel/`): WebKit has no CDP, so
  `Input.dispatchMouseEvent` / `Input.dispatchTouchEvent` do not exist. Pen and finger strokes are
  synthesized `PointerEvent`s dispatched in the page (`pointerType` `"pen"` / `"touch"`, a pressure
  curve, `tiltX/tiltY`, `width/height`), densified to 2 px and delivered two moves per animation frame
  (a 120 Hz Pencil at 60 Hz); the mouse is Playwright's real WebKit mouse. Three consequences: (1)
  untrusted events never reach WebKit's native gesture layer, so the rubber-band, pull-to-reload,
  double-tap zoom, long-press callouts, the on-screen keyboard and focus zoom cannot be produced at all
  (checked through computed CSS and emulation instead, and listed for the device); (2) WebKit refuses
  `setPointerCapture` for a pointer id it never saw, so synthetic strokes use id 1 and the pinch test
  patches capture (test harness only); (3) an untrusted event's `getCoalescedEvents()` is empty, and
  with a desktop UA tldraw reads moves from it, so the harness returns `[event]` for untrusted events
  (a real event lists itself).
- Older iPadOS was emulated by deleting, before any page script ran, the built-ins WebKit added after
  the version under test (`w06-oldapi.mjs`, `w07-pdf.mjs`), plus a parse of every shipped chunk as
  ES2023 (`syntax-audit.mjs`). The keyboard was emulated by replacing `window.visualViewport` with a fake
  that shrinks and pans the way iPadOS Safari's does (`w12-keyboard.mjs`).
- Scripts, logs and screenshots: the session scratchpad, `webkit/w00…w21-*.mjs`, `webkit/shots/`; the
  key before/after shots are `docs/qa-screenshots/webkit-*.png`. The machine was shared with two other
  agents (load average 20–48); a few AI calls timed out on the first compile of a route and were re-run.

## Which Safari the app supports

Next 16's default browserslist is `chrome 111, edge 111, firefox 111, safari 16.4` (no
`.browserslistrc` here), Tailwind v4's CSS (`@property`, `color-mix()`, `oklch`) needs Safari 16.4, and
Next's polyfills only cover old built-ins (`Array.prototype.at`, `Object.hasOwn`, `URL.canParse`…). So
the effective floor is **iPadOS / iOS 16.4**: every iPad from the 5th generation (2017) up can run it;
an iPad Air 2 or mini 4 (iPadOS 15) cannot, and gets no message saying so.

Checked against that floor:

- Syntax: all 80 client chunks of the production build parse as ES2023 (no RegExp `v` flag, regex
  modifiers or duplicate named groups); no CSS nesting in the built CSS.
- APIs: the app's own client code uses nothing newer than 16.4 (`AbortSignal.any/timeout` only on the
  server; the Ask client keeps its own AbortController on purpose; `structuredClone`, `findLast`,
  `toSorted` are ≤ 16.0). In the built chunks, the only unguarded post-16.4 calls were in pdf.js
  (finding 1); tldraw's `checkVisibility` is feature-tested; no `requestIdleCallback` (Safari has none).
- Run with the post-16.4 built-ins removed (Set methods, `Promise.withResolvers`, `Object/Map.groupBy`,
  `AbortSignal.any`, `checkVisibility`, `URL.parse`, `Promise.try`, base64/hex on `Uint8Array`,
  `RegExp.escape`, iterator helpers, `getOrInsert*`, `Error.isError`): sign-in, the boards home, a new
  board, a pen line read back by Live, Ask, Lecture's consent, a new screen, the account page and a
  reload all work with no error. Only the PDF reader failed (finding 1).

### 1. PDF upload broken on iPadOS 16.4–18 — broken (Feature Labs)

Repro (`w07-pdf.mjs`): switch on the PDF extra, open a board, PDF → choose a two-page worksheet.
WebKit 26.6 as shipped: the thumbnails, then the page on the board. With the built-ins of an older
Safari removed: up to 17.3 "Couldn't read this PDF" (`Promise.withResolvers is not a function`); 17.4
"Reading PDF…" for ever (`Promise.try is not a function`, an unhandled rejection in the worker set-up);
18.x "Couldn't read this PDF" (`this.#methodPromises.getOrInsertComputed is not a function`).

Cause: pdf.js 5.7's modern build (`pdfjs-dist`, page and worker) calls `Map.prototype.getOrInsertComputed`,
`Promise.try`, `URL.parse`, `Uint8Array.fromBase64` and `Promise.withResolvers` with no fallback. iPadOS
Safari has the first ones only from 26.x, so the reader failed on every iPad not on the newest iPadOS.

Fix (`src/lib/pdf.ts`): load `pdfjs-dist/legacy/build/pdf.mjs` and its legacy worker from unpkg; the
legacy build carries core-js polyfills for all of them and targets Safari 16.4. Still lazy (the board's
first load is unchanged; the lazy PDF chunk is 118 → 137 KB gzip). A failed load is no longer cached,
so the dialog's Retry really retries. After: the page lands on the board with the 17.0, 17.4 and 18.0
built-ins removed and on 26.6. Test: `src/lib/__tests__/pdf.test.ts`. Screenshots:
`webkit-before-pdf-ipados17.png`, `webkit-after-pdf-ipados17.png`.

### 2. A lecture stops when the iPad locks itself — broken / lost work (needs the device)

A lecture is minutes of listening with no touch on the screen. iPadOS locks the screen after its
auto-lock delay (2 minutes by default) and Safari suspends a page behind a locked screen; the
microphone track and the transcriber's connection stop, and nothing tells the student until they
unlock. An audio-only capture is not known to keep iOS awake (video playback is what holds the
display); the Screen Wake Lock API (Safari 16.4+) does.

Fix (`src/components/lecture/wakeLock.ts`, `lectureRunner.ts`, `lectureRuntime.ts`): the runner holds a
screen wake lock while the lecture is starting or listening, releases it when paused, stopped or
failed, and asks again when the page comes back into view (browsers drop the lock on hide). Missing or
refused, nothing changes. In the lazy lecture chunk. Tests: `wakeLock.test.ts`, `lectureRunner.test.ts`.
WebKit: a scripted lecture requests the lock (`WakeLock.prototype.request("screen")`) and it is
released on stop. Whether the screen really stays on, and whether the old behaviour really stopped the
mic, needs an iPad (check 6 below).

### 3. The keyboard over Ask on an iPad held sideways — janky

On iPadOS Safari the on-screen keyboard shrinks only the visual viewport. The board's root is
`position: fixed; inset: 0`, so when the Ask box takes focus Safari pans the page to bring it into
view. Emulated on an 11" iPad sideways (1194x834, keyboard ~404 px, `w12-keyboard.mjs`): the visible
part is y 375–805; the back button, the help tabs, the panel's header and the whole top half of the
board (where the tutor writes the answer) are out of view, and the board is 834x834 of which the
student sees the bottom half.

Fix (`src/components/board/keyboardFit.ts`, wired in `src/app/board/[id]/page.tsx`): while a field in
the Ask panel has focus, the panel is docked beside the board (`md:landscape:`), at least 40 px are
hidden and at least 360 px stay visible (an iPad's numbers, not a phone's), and the page is not
pinch-zoomed, the root is laid over the visible box (`top = visualViewport.offsetTop`,
`height = visualViewport.height`); the board refits (`useScreenCamera`) and everything goes back when
the keyboard does. After, same emulation: root 0,375–1194,805, back button, panel header and text box
all in view, board 834x430 with the whole screen in it (zoom 0.501 → 0.429), and back to 834x834 when
the keyboard goes. The root is now positioned by class (`fixed inset-0`), so clearing the inline
top/height falls back to `inset: 0`. Upright (the bottom sheet) nothing changes: tried, the fitted
board was a 275 px strip mostly covered by its own bars, worse than Safari's panning, so it was limited
to the docked layout. Tests: `src/components/board/__tests__/keyboardFit.test.ts`. Screenshots (what
the student sees, the visual viewport): `webkit-before/after-ipad-keyboard-ask-sideways.png`. The real
keyboard needs an iPad (check 3).

### 4. A text field zooms an iPhone's board in for good — broken on iPhone

Computed in WebKit at 390 px: the Ask box, the readback editor (`MathEditor`), the bug report, the
board search and the sign-in fields are all 14 px (only the account page's name field is 16 px).
iOS Safari zooms the page in when a field under 16 px takes focus. On the board that zoom could not be
undone: tldraw calls `preventDefault` on `gesturestart` for the whole document, so a pinch zooms the
canvas, never the page. The board route now has its own viewport with `maximum-scale=1`
(`src/app/board/[id]/layout.tsx`), which stops the automatic zoom; iOS ignores it for pinch-zoom, so no
zoom a student could use is lost. Checked in WebKit: the board's meta after a client-side navigation
from the boards home, and the root one again after going back. iPads in Safari's default desktop mode
do not zoom on focus (to confirm, check 4). The platform pages keep their zoom (see "Other lanes").

### 5. Rubber-band and pull-to-reload on the board — janky (iOS)

The canvas is `touch-action: none`, but the top bar, the toolbar and the Ask panel let a drag through
to the page, and iOS Safari bounces even a page that does not scroll, and pulls it down to reload.
`html`/`body` were `overscroll-behavior: auto`. Now `none` on the board page only
(`html:has([data-board-root])`, Safari 16+), so the boards home and account keep their normal bounce.
Verified as computed values in WebKit (none on the board, auto after leaving it); the gesture needs a
device (check 2).

### 6. "Needs Chrome, Edge or Safari", shown in Safari — confusing

Without a realtime recognizer (no `ELEVENLABS_API_KEY`), lecture falls back to the browser's
recognizer. Safari's answers `service-not-allowed` when its speech service is off on the device
(Dictation off, or Speech Recognition not allowed for Safari); that mapped to `unsupported`. Now its own
code, `speech-off`: "Speech recognition is turned off. On an iPad, turn on Dictation (Settings ›
General › Keyboard) and allow Safari in Settings › Privacy & Security › Speech Recognition, then try
again." with Try again. Tests in `speechSources.test.ts`, `lectureView.test.ts`; WebKit with the
recognizer answering `service-not-allowed`: `webkit-after-lecture-dictation-off.png`.

Also checked (no change): a refused microphone (`not-allowed`) says "Lecture mode needs your
microphone…" with Try again; no recognizer and no audio APIs at all says "needs Chrome, Edge or
Safari"; WebKit sends no `end` after a fatal error and the source does not rely on one. With the
permission prompt unanswered the bar stays on "Starting the microphone…" with Cancel (as in Chromium).
The realtime path's `new AudioContext()` is created after `getUserMedia` resolves, outside the tap;
WebKit lets a capturing page start audio, so `resume()` should not hang (check 6).

### 7. Error reports: Safari's lifted-pen error — polish

The reporter drops tldraw's `setPointerCapture` failure by Chrome's words ("No active pointer with the
given id"). WebKit throws `NotFoundError: The object can not be found here.`, its message for every
NotFoundError. Now noise only when the stack's top frame is `setPointerCapture@[native code]` (what
WebKit 26.6 gives); the same words from `removeChild` are still reported. WebKit: an unknown pen
pointer on the canvas throws it and nothing is sent, while an ordinary error on the same page is.

### 8. Return says "return" in the Ask box — polish

`enterKeyHint="send"`: the on-screen keyboard labels the key "send" (it sends).

### 9–12. Not fixed

- **9. The palm before the first Pencil stroke.** tldraw switches to pen mode (fingers no longer draw)
  at the first pen event of a session, and a board always opens with pen mode off. A palm that lands
  before the Pencil's first stroke draws a mark, which Live then reads. After the first Pencil stroke
  palms are ignored (verified: a finger stroke after a pen stroke adds nothing; two fingers still pinch).
  Starting boards in pen mode on a device that has used a Pencil would fix it, but a student whose
  Pencil runs flat could then not draw with a finger (the menu with tldraw's pen-mode switch is hidden).
  A product call; a remembered "this device writes with a Pencil" plus a visible finger-drawing toggle
  would cover both.
- **10. tldraw and the iPad's desktop user agent.** `tlenv.isIos` is false on iPadOS Safari (it looks
  for "iPad" in the UA), so tldraw uses `getCoalescedEvents()` for pen moves (WebKit 26.6 has it; with
  trusted mouse events every move arrived: 243 of 243) and skips its iOS-only paths (hiding the toolbar
  while editing text, the iOS input-scroll fix). That is also how tldraw.com behaves on an iPad. Not
  changed.
- **11. Backups and Safari's storage quota** (sync lane): see "Other lanes".
- **12. iPadOS 15 and older.** A page compiled for Safari 16.4 with Tailwind v4 CSS; no message. A tiny
  inline feature check in the root layout could show one; not done (iPad Air 2 / mini 4 only).

## Other lanes (found, not changed here)

- **Sync / backups (`fix/sync-followups`):** (a) WebKit's localStorage quota is 5,238,281 characters
  for an ASCII value, as in Chromium, but **2,613,281** once the value holds any character above U+00FF
  (WebKit stores it as UTF-16 and counts bytes; Chromium measured the same 5.2 M either way). A backup
  of up to `BACKUP_MAX_BYTES` (2,000,000 characters) with one "√" in it costs 4 MB of the origin's
  5 MB in Safari, so a second board's large backup does not fit; `write` then clears that board's older
  backup and returns false. Measuring the cap in bytes (2 per character when any is > 0xFF), a lower
  cap for Safari, or IndexedDB would fix it. (b) Safari's tracking prevention deletes all
  script-writable storage of a site after 7 days of Safari use without visiting it: a backup not
  restored within that window is gone (and the student is signed out). (c) The double "Restored"
  toast in dev only (likely StrictMode).
- **Feature Labs PDF:** an inserted page is placed larger than the 16:9 screen (it overflows the frame),
  in WebKit as in Chromium.
- **Login layout (`fix/release-polish`):** the sign-in fields and the boards search are 14 px; an iPhone
  zooms in when they take focus (users can pinch back out on those pages). 16 px on touch screens
  (`@supports (-webkit-touch-callout: none)` or `pointer-coarse:`) would stop it.
- **Ink meter (board bar):** on an upright iPad (810–834 px) the "300 ink" pill pushes "Report a bug"
  onto a second row of the bar (one row in the feel pass, before the meter existed); not WebKit-specific.
- **Environment:** the shared stack's Storage still fails uploads (42P10, reliability N7); the first
  compile of a dev route can exceed the client timeouts (recognize 6 s, Ask 60 s) under this load.

## Check on a real iPad (about 5 minutes)

Safari on an iPad with an Apple Pencil, no hardware keyboard, signed in, on the deployed build:

1. **Pencil and palm.** Open a new board. Rest your palm on the screen, then write `2x + 3 = 11` with the
   Pencil. Does the palm leave a mark (finding 9)? Write a second line with the palm resting: no marks
   now? Pinch with two fingers: the board zooms, the page does not.
2. **No bounce, no reload.** With a finger, drag down from the top bar, and up from the toolbar. The page
   must not bounce or start a pull-to-reload. Double-tap a button in the bar: no page zoom.
3. **Ask sideways with the keyboard.** Hold the iPad sideways, open Ask, tap the text box. With the
   keyboard up you should see the back button, "Ask the tutor ×", the text box and the whole screen
   (smaller). The return key says "send". Ask "2 two-step equations", watch them being written, then tap
   the board: the keyboard goes and the board returns to full size with nothing left shifted. Upright:
   the text box stays above the keyboard (Safari scrolls to it) and the page is back in place after.
4. **Focus zoom.** Open the bug report and tap its text box, and double-tap a readback to edit it: the
   page must not zoom in (on an iPhone too, if one is at hand).
5. **PDF (only if the PDF extra is on).** Settings › General › About: note the iPadOS version. Upload a
   one-page PDF: thumbnails, then the page on the board.
6. **Lecture.** Settings › Display & Brightness › Auto-Lock: 2 minutes. Start a lecture, put the iPad
   down and talk (or play a video lecture) for 3 minutes without touching it: the screen must stay on and
   the words keep coming. Stop: the iPad locks after 2 minutes again. If Dictation is off (Settings ›
   General › Keyboard), Lecture should say how to turn it on (only when the deployment has no
   ElevenLabs key).
7. **Leave and come back.** Draw a stroke, switch to another app at once, wait 10 s, come back: the stroke
   is there and the pill says Saved.

### 2. Backups and Safari's quota (finding 11)

`src/lib/sync/localBackup.ts`. The 2,000,000 cap is now in bytes as WebKit counts them
(`storedBytes`: 1 per character when every character is Latin-1, 2 per character once any is above
U+00FF), so a backup with a "√" is capped at 1 M characters and two of the largest backups (4 MB)
fit in Safari's 5 MB beside the session. When a write throws QuotaExceededError the backup is tried
again without its `base` / `sent` copies, then room is made by evicting, oldest first, backups this
tab has already restored (`absorb`, called by `restoreDeviceBackups` before it writes its own), then
unreadable ones, then ones older than 7 days (`STALE_BACKUP_MS`); never another tab's or board's
recent backup and never a non-backup key. If it still does not fit (or is over the cap), the write
returns false and this tab's previous backup stays (it used to be cleared): older unsaved work beats
none, and a restore is record by record and base-aware. A blocked storage (SecurityError) evicts
nothing. Tests (`localBackup.test.ts`, `restoreDeviceBackups.test.ts`) use a fake Storage that
meters keys and values the way WebKit does (Latin-1 vs UTF-16, a byte quota, a failed write changes
nothing); the restore test fails without `absorb`. Not re-measured in a browser (the quota numbers
are the WebKit probe's above).

### 3. Safari's 7-day storage eviction — checked, no change

Safari deletes all of a site's script-writable storage (the backups, and the session) after 7 days
of Safari use without a visit. No fix exists in the page; what matters is that a backup is rarely
the only copy, and that the student can see when it is. Checked in WebKit on an upright iPad
(`f05-saved.mjs`): a change reaches the server 2.0–2.4 s later (first PATCH at 2,388 ms; the pill
shows the spinner at 2.0 s, "Saved" at 2.5 s, nothing from 4 s); a hidden tab saves at once
(visibilitychange, above). Offline: "Unsaved changes — offline" in amber (tooltip "You're offline.
Changes will be saved when the connection returns.") for as long as the board is open, and the
backup key is written; back online: Retrying… → Saved and the backup is removed. So a backup only
outlives a session when a save could not land, and the bar says so in words (those states never
shrink to an icon). Not done (ideas): a note on the boards home for boards with unsaved work on this
device; telling iPad users that a Home Screen web app keeps its own storage clock.
